# План реализации rundevrun

Основа: [PRD 0.4](PRD.md). Статус: этапы 0 и 1 приняты; этап 2 в работе.

Цель первой версии: заменить текущий launcher MillDrum универсальным CLI для агента и подтвердить работу на втором проекте. Промежуточные этапы пригодны для проверки, но не считаются готовым релизом.

## Роли

- Sol оркестрирует работу: читает требования, формирует задания, выбирает следующий готовый этап, интегрирует результаты, проверяет соответствие PRD и ведёт статус. Sol самостоятельно исправляет небольшие интеграционные ошибки.
- Terra реализует ядро процессов, состояние, зависимости, переключение, proxy, публикацию и миграцию MillDrum. Каждое задание ограничено одним проверяемым результатом.
- Luna реализует ограниченные задачи по утверждённым контрактам: конфигурацию, discovery, CLI, документацию и вспомогательные проверки. При необходимости менять модель состояния или lifecycle возвращает вопрос Sol, а не расширяет задачу.
- Astra проверяет критические решения и реализацию по запросу Sol. Проверка заканчивается конкретными дефектами, сценариями воспроизведения и оценкой оставшегося риска. Astra не становится вторым постоянным оркестратором.

Имена моделей для заданий: Sol `gpt-6.1-sol`, Terra `gpt-6.1-terra`, Luna `gpt-6-luna`, Astra `gpt-6-astra`. Это назначение ролей пользователем, а не требование автоматически заменять недоступную модель. Параметры reasoning и runtime отдельно не переопределяются без необходимости.

## Порядок работы Sol

1. Прочитать инструкции репозитория, PRD, этот план и текущий git status. Сохранить чужие изменения. До начала реализации закрепить исходные документы и выбранную базу в рабочей ветке согласно действующим правилам репозитория.
2. Выполнять только задачи с завершёнными зависимостями. Перед передачей задачи записать её владельца, границы файлов и критерии приёмки.
3. Выдавать Terra и Luna небольшие задания с явным контрактом. Не передавать целиком PRD с просьбой «реализовать всё».
4. Принимать результат по изменённому коду, выполненным проверкам и поведению. Отчёт builder сам по себе не означает готовность.
5. Интегрировать принятые изменения, запускать проверки на общей версии и только затем открывать зависимые задачи.
6. Если меняется общий контракт, остановить затронутую параллельную работу, обновить спецификацию и задания. Не исправлять несовместимые реализации дополнительными слоями адаптеров.
7. После каждого этапа обновлять журнал исполнения и сообщать пользователю, что работает, что проверено и что ещё требуется.

По умолчанию одновременно работают Sol и не более двух builders. Четвёртый слот можно использовать для точечной проверки Astra. Builders не создают дочерних агентов.

При общей директории разные builders не редактируют один файл. `go.mod`, `go.sum`, общие типы, точку входа CLI и CI в каждый момент меняет один назначенный владелец. Sol назначает конкретные пути после появления структуры проекта. Предлагаемые ниже границы относятся к ответственности, а не требуют заранее создавать пустые пакеты.

Если нужна изоляция checkout или настройки модели, использовать доступный механизм `delegate_task`, предварительно проверив `orchestrator_capabilities`. В остальных случаях использовать native delegation с явно назначенной моделью и самостоятельным текстом задания. Не создавать top-level threads и shell worktrees для подзадач. Следовать действующим правилам инструмента ожидания и отмены задач; недоступную модель не заменять молча.

## Общие правила приёмки

- Любая задача имеет воспроизводимую проверку своего результата. Документация и простая разметка вывода не требуют искусственных unit tests.
- Код не знает встроенных ролей backend/frontend. В примерах используются произвольные `api`, `console`, `admin`, `worker`.
- Для тестов используются временные проекты, runtime-каталоги и данные. Рабочие процессы и база MillDrum не становятся тестовыми fixtures.
- Состояние после ошибки должно совпадать с тем, что сообщает CLI. Частичная операция не маскируется успешным exit code.
- Проверки Linux и macOS выполняются на соответствующих ОС. Кросс-компиляция не заменяет тесты lifecycle.
- Недоступность macOS, второго проекта или пользовательского домена отмечается как непроверенная часть приёмки. Она не мешает независимой работе и не даёт права объявить релиз готовым.
- Не добавлять GUI, собственный DNS/CA/ACME, управление Git worktree или автоматический crash restart. Эти функции не нужны для согласованной версии.

## Этап 0. Контракты и карта переноса

Владелец: Sol с ограниченным исследованием Terra. Зависимости: нет.

Прочитать текущие `internal/devrunner`, `internal/procid` и вызывающий их код MillDrum. Зафиксировать commit источника: ранее исследовался `1184e35`, но перед переносом нужно проверить актуальную версию. Не переносить по одному только списку файлов из PRD.

Создать `docs/TECH_SPEC.md` с конкретными контрактами:

- Идентичность проекта, worktree и экземпляра, разрешение селекторов и локальных привязок.
- Версия `dev.toml`, команды, escaping подстановок, окружение сборки/запуска/hooks, приоритеты значений и таймауты.
- Файл пакетной операции: соответствия исходных и целевых экземпляров, проверки дубликатов, пересечений и циклов.
- Состояния экземпляра, запись намерения перед запуском, фактическое состояние процесса и восстановление после обрыва CLI.
- Блокировки и границы их удержания, назначение портов, проверка владения процессом.
- Единый план действий для dry-run и исполнения. Dry-run ничего не запускает и не резервирует; исполнение повторно проверяет входное состояние.
- JSON envelope, стабильные ошибки, exit codes, представление частичного результата и граница раскрытия секрета `share`.
- Контракты между операциями, супервизором, proxy и публикацией. Никаких интерфейсов только «на будущее».

Составить карту функций старого launcher и их нового владельца: универсальное ядро, конфигурация MillDrum, проектный скрипт или обёртка. Особо проверить backup после остановки, agent shutdown, watcher, seed, sign-in, OAuth preview и совместимость cookies. Отсутствие встроенных исключений MillDrum в новом gateway не должно незаметно сломать старый сценарий: определить проектный способ его сохранить.

Выход: спецификация, минимальный Go module и точка входа, версия инструментария, карта переноса. Примеры конфигурации и JSON согласованы между собой. Создание тестовых helpers допускается только когда их использует первая проверка.

Точка проверки Astra A0: граф зависимостей, switch, восстановление состояния и граница данных MillDrum. Sol запрашивает одну проверку до параллельного строительства. Неясность, меняющая продуктовый смысл, возвращается пользователю; детали реализации Sol решает по PRD.

## Этап 1. Конфигурация, discovery и состояние

Два независимых задания после этапа 0.

Luna, задача 1A: конфигурация и discovery. Реализовать чтение и проверку схемы, поиск корня, регистрацию проектов, существующие Git worktree, перечисление сервисов без запуска. Ошибки включают путь к полю. Учесть symlink, detached HEAD, одинаковые имена независимых clone и неоднозначную ветку.

Terra, задача 1B: состояние и идентичность процессов. Перенести необходимые части `procid`, атомарное хранение и блокировки без зависимостей от MillDrum home/owner. Реализовать состояние экземпляров и запусков, права доступа, сверку stale state. Не реализовывать универсальное управление данными приложения.

Проверки 1A: валидный и ошибочный TOML, неизвестная версия, коллизии идентичности, отсутствие выполнения команд при discovery.

Проверки 1B: параллельные изменения registry, прерванная запись, устаревший PID, различение живого чужого процесса. Тесты PID reuse не должны зависеть от случайного переиспользования PID ОС.

Sol интегрирует результаты и проверяет, что зарегистрированный незапущенный сервис виден в состоянии. Приёмка PRD: части 5, 7, 18.

## Этап 2. Первый работающий запуск

Основной владелец: Terra. Зависимости: 1A и 1B.

Реализовать полный путь для одного сервиса: план адреса, build в отдельный run-каталог, окружение, detached supervisor, readiness, лог, status, stop, restart. Поддержать сервис без порта. Сохранить намерение до spawn, чтобы следующий CLI мог найти процесс при аварии предыдущего.

Luna параллельно делает только оболочку этих команд, текстовый/JSON вывод и help по зафиксированному контракту. Алгоритмы запуска не дублируются внутри CLI. Sol назначает одного владельца файлов команды и общей точки входа.

Проверки: CLI завершился, а сервис работает; повторный up не создаёт копию; timeout и отмена build очищают дочерние процессы; stop завершает принадлежащие процессу дочерние процессы; чужой владелец порта остаётся жив; ошибка новой сборки сохраняет старую версию. Логи ограничены ротацией, сбой записи не скрывается.

Выход: через настоящий бинарник можно запустить и остановить временный сервис, получить один JSON-документ в stdout и найти логи. Приёмка PRD: 6, 7 и основа 17, 18.

## Этап 3. Зависимости и окружение нескольких worktree

Владелец: Terra. Зависимости: этап 2.

Реализовать граф экземпляров, явный bind, назначение всех необходимых портов до build/start, подстановки адресов и порядок readiness. Поддержать общую зависимость, независимые наборы, смешанный набор worktree и процесс без HTTP.

Реализовать down с защитой внешних потребителей и явным cascade. Остановка потребителя не останавливает его зависимости. Все селекторы проверяются до первого изменения.

Luna может параллельно собрать небольшой пример монорепозитория и CLI-сценарий его запуска. Он использует публичные команды, а не внутренние функции executor; набор сервисов должен отличаться от MillDrum.

Проверки: два потребителя общей зависимости, независимые зависимости, цикл, конфликт переменных после нормализации, занятый порт между планом и bind, корректное окружение build и запуска, отсутствие подмены выбранной зависимости. Прямые URL не путаются с URL браузера.

Выход: агент создаёт смешанное окружение из нескольких worktree без ручного выбора портов. Приёмка PRD: 2–5, 17, 18.

## Этап 4. Hooks и пакетное переключение

Владелец: Terra. Зависимости: этап 3.

Сначала реализовать hooks и замену одного сервиса через общий план операций. Затем расширить тот же путь на список и файл соответствий. Один executor обслуживает одиночное и пакетное переключение.

Подготовить все новые сборки до остановки старых экземпляров. Вычислить затронутых потребителей, не затрагивать независимые сервисы. Каждый экземпляр проходит переход один раз. После изменения адресов перезапустить потребителей с корректным окружением и обновить только нужные привязки.

Проверки: разные целевые worktree в одном наборе; сервис одновременно выбран и является зависимостью; целевой экземпляр уже работает; отсутствие сервиса в целевой конфигурации; ошибки каждого hook; прерывание CLI после каждой границы изменения состояния. После частичного сбоя JSON и последующий status должны совпадать.

Точка проверки Astra A1: процессная идентичность и завершение дерева, блокировки, orphan cleanup, частичный switch и отсутствие автоматического отката данных. Дать Astra интегрированный код этапов 1–4 и результаты проверок.

Выход: Sol принимает все существенные замечания до перехода к миграции. Приёмка PRD: 8, 19 и lifecycle-части 7, 11.

## Этап 5. Локальные адреса и HTTPS

Владелец: Terra. Зависимости: этап 3 и контракт уведомления proxy об изменении экземпляров из этапа 0. Можно выполнять параллельно этапу 4 при разных владельцах кода и свободных слотах.

Реализовать loopback proxy, плоские hostname, коллизии имён, маршруты к готовым экземплярам, 404/503 и обновление маршрута после restart. Связать адрес с идентичностью экземпляра, чтобы освобождённый порт не направил трафик в другой процесс.

Загрузить предоставленные сертификаты, проверять SAN, ключ и срок, выбирать по SNI и выполнять reload с сохранением прежней конфигурации при ошибке. Поддержать ручную конфигурацию входа на 443, в том числе заранее настроенную пересылку на локальный listener. TLS, завершённый внешним proxy, допускается только с явно настроенным доверием к этому proxy.

Проверить WebSocket/HMR, потоковые ответы, SSE, cookies и явные маршруты к HTTP-зависимостям. Не менять CORS и allowed hosts приложения автоматически.

Luna по контракту реализует `proxy status`, `open`, диагностику DNS/listener/TLS/маршрута и инструкцию подключения готового домена. DNS, выпуск сертификатов и trust store не изменяются.

Автотесты используют временные тестовые cert/key без установки CA в систему. Отдельная интеграционная проверка использует подготовленный пользователем домен Cloudflare. Отсутствие реального домена не мешает автоматическим проверкам, но остаётся пунктом приёмки.

Выход: постоянный HTTPS URL работает при смене внутреннего порта. Приёмка PRD: 13–16, локальная часть 20.

## Этап 6. Share и snapshot

Владелец: Terra. Зависимости: этапы 4 и 5.

Перенести парольную защиту и управление `cloudflared`, обобщить gateway. Live публикует выбранный HTTP-сервис. Snapshot собирает отдельные статические артефакты с явными маршрутами к зависимостям и пригодным для публикации окружением.

Публикация принадлежит конкретному экземпляру. Down/switch закрывает затронутые публикации, unshare сохраняет локальные процессы. Не переносить встроенные маршруты, cookie stripping, Origin rewrite и login script MillDrum в универсальное поведение.

Проверки: без пароля закрыты статика, API и WebSocket; cookies приложения продолжают работать; прежняя публикация сохраняется при ошибке новой сборки; новая публикация не принимает старую сессию; секрет не появляется в status/logs; сбой cloudflared не останавливает сервис. Для offline-проверок использовать управляемый subprocess вместо реальной сети, затем отдельно провести реальный share.

Точка проверки Astra A2: маршрутизация Host/SNI, доступ только к зарегистрированным целям, граница пароля, заголовки и cookies, обращение с секретами, live/snapshot и взаимодействие со switch. Проверить интеграцию этапов 4–6, а не только отдельные пакеты.

Выход: работают оба режима публикации, известные ограничения Quick Tunnel отражены в документации. Приёмка PRD: 9, 10, внешняя часть 20.

## Этап 7. Замена launcher MillDrum

Владелец: Terra; Sol отвечает за согласованность двух репозиториев. Зависимости: этапы 4–6 и закрытые существенные замечания A1/A2.

До изменения MillDrum прочитать его AGENTS.md; для запуска использовать его run-milldrum skill. Работать по карте переноса этапа 0. Изменения MillDrum держать отдельно от изменений универсального runner, с явными версиями совместимости.

Добавить конфигурацию сервисов и тонкую обёртку `./dev`. Сохранить проектные backup, agent shutdown, seed, sign-in, exec, watcher и preview-поведение. Для параллельных экземпляров, использующих SQLite, назначить разные каталоги данных. Для последовательного switch сохранить backup после остановки и до запуска новой версии.

Сначала проверить всё на отдельном runtime и копии тестовых данных. Реальное переключение пользователя выполнять только после успешной проверки: остановить старый launcher, затем запустить новый. Не допускать одновременного управления теми же процессами. Не удалять старый launcher или данные до подтверждённой приёмки; предусмотреть описанный путь возврата без автоматического отката схемы БД.

Проверить каждый пункт карты переноса старой и новой командами. Совпадение названий команд не заменяет проверку поведения. Пункты, перенесённые в обёртку, также входят в готовность первой версии.

Точка проверки Astra A3 вызывается, если адаптация меняет блокировки данных, backup, порядок остановки агентов или ранее проверенную границу preview. Если адаптация использует проверенные контракты без изменения этих механизмов, Sol проводит обычную проверку и фиксирует основания не вызывать Astra.

Выход: ежедневная работа MillDrum обходится без старого launcher. Приёмка PRD: 11, 21 и часть 1.

## Этап 8. Проверка универсальности и выпуск

Владельцы: Sol принимает; Luna готовит инструкции и сценарии CLI; Terra устраняет обнаруженные дефекты. Зависимости: этап 7.

Подключить второй реальный проект без проектных условий в коде runner. Если проект ещё не выбран, Sol запрашивает его у пользователя; учебный пример этапа 3 полезен, но не заменяет этот критерий.

Провести агентный сценарий через публичный CLI: discovery, выбор экземпляров, dry-run, up, bind, switch одного и набора, разбор ошибки, status, logs, share и down. Проверить, что агенту достаточно help и JSON и не приходится читать внутреннее состояние на диске.

Запустить проверки на Linux и macOS, включая реальные process groups и shutdown. Для готовой кодовой базы базовый набор: форматирование, `go vet ./...`, `go test ./...`, затем `go test -race ./...` на поддерживаемой среде. OS-specific проверки и сетевые сценарии перечисляются отдельно. Сборка бинарника и инструкция установки должны быть воспроизводимыми.

Создать `docs/ACCEPTANCE.md`: каждый критерий PRD 1–21 связан с командой или сценарием, платформой, проверенным commit, результатом и оставшимся ограничением. Не заполнять результат «пройдено» заранее.

Выход: все обязательные критерии подтверждены, существенные замечания закрыты, пользовательская настройка и миграция описаны. Публикация релиза, push и merge выполняются только в рамках полученной на тот момент авторизации.

## Параллельная работа

После этапа 0 одновременно выполняются 1A и 1B. На этапе 2 Terra делает lifecycle, Luna оболочку CLI. На этапе 3 Luna может готовить пример и сценарии. После этапа 3 этапы 4 и 5 можно выполнять двумя отдельными заданиями Terra; Luna в это время не запускается третьим builder. Перед этапом 6 обе ветви должны быть интегрированы.

Этапы 6 и 7 последовательны. Документация и подготовка приёмочных сценариев Luna могут идти параллельно с Terra, если используют уже принятые контракты. Не запускать работу заранее только ради заполнения слотов.
