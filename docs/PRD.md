# PRD универсального devrunner

Статус: черновик для обсуждения, версия 0.4.
Дата: 13 ноября 2026.
Рабочее название проекта: rundevrun. В примерах имя бинарника `rdr`; окончательное имя пока не выбрано.

## Задача

Одно установленное приложение управляет локальными процессами разработки в разных проектах и Git worktree. Проект описывает свои команды в конфигурации. Разработчик запускает нужные сервисы, видит их состояние и логи, переключает версии и при необходимости делится защищённой ссылкой.

Основой служит devrunner из MillDrum. Его управление процессами и публикацией переиспользуется там, где оно не зависит от устройства MillDrum.

## Принятые решения

- Первая версия предоставляет CLI для coding agents. Графический интерфейс появится позже.
- В модели есть произвольные сервисы и зависимости между ними. Backend и frontend могут быть именами сервисов, но не встроенными типами или особыми ролями.
- Сервисы из разных веток и worktree могут работать одновременно. Один экземпляр может быть общей зависимостью нескольких других; можно запускать и независимые наборы.
- Агент может переключить один сервис, выбранный набор или все сервисы указанного worktree одной командой. Цели операций указываются явно.
- Первая готовая версия должна заменить текущий runner MillDrum, включая используемые сценарии запуска, переключения, пересборки и публикации.
- Локальные адреса доступны только на своём компьютере. Доступ другим людям предоставляется отдельной командой `share`.
- Основной формат адреса: `{service}-{worktree}-{project}.{domain}`, например `console-feature-milldrum.dev.example.com`.
- Первый сценарий настройки использует личный домен с DNS в Cloudflare. Пользователь самостоятельно готовит DNS, сертификат, ключ и доступ к локальному входу HTTPS. Утилита использует готовые настройки.
- Выпуск и продление сертификатов, управление Cloudflare DNS и первоначальная системная настройка не входят в ответственность runner.
- Runner назначает порты до запуска сервисов и передаёт собственные адреса и адреса выбранных зависимостей через окружение.
- Данные, seed, авторизация и управление агентами MillDrum остаются в MillDrum.

Далее описан предлагаемый контракт поведения для этих решений. Точные схемы конфигурации и CLI фиксируются в технической спецификации.

## Пользователь и основные сценарии

Основным пользователем CLI будет агент, работающий по заданию разработчика. Ему нужно обнаружить конфигурацию проекта, однозначно выбрать сервисы, выполнить операцию и проверить результат без интерактивного диалога. Человек должен понимать те же команды и их текстовый вывод.

1. Запустить выбранные сервисы монорепозитория и их зависимости одной командой.
2. Одновременно запустить `console` из worktree A, `admin` из B, `api` из C и `worker` из A.
3. Подключить несколько сервисов к одному экземпляру `api`, либо запустить независимые экземпляры `api` и явно распределить потребителей между ними.
4. Переключить только `console`, сохранив остальные сервисы; переключить выбранный набор либо все сервисы исходного worktree одной операцией.
5. До переключения получить список затронутых экземпляров, их зависимостей и публикаций. После операции получить фактический результат для каждого экземпляра.
6. Из любой директории посмотреть процессы всех проектов, найти сбой и прочитать логи.
7. Закрыть терминал или завершить агента и продолжить управление работающими процессами из другой сессии.
8. Открыть сервис по именованному HTTPS URL на своём компьютере или явно опубликовать его через `share`.
9. Заменить старый launcher MillDrum и продолжить привычные сценарии через новую утилиту и проектную обёртку.

## Границы первой версии

В первую версию входят:

- Один устанавливаемый Go-бинарник для Linux и macOS.
- Конфигурация произвольного набора долгоживущих сервисов, включая процессы без HTTP и без порта.
- Регистрация нескольких проектов и обнаружение существующих Git worktree.
- Запуск, остановка, перезапуск и переключение отдельных сервисов и явно выбранных наборов, в том числе из разных worktree.
- Явные зависимости между экземплярами сервисов, включая другие worktree того же проекта.
- Автоматические либо фиксированные порты, передача адресов зависимостей в окружение.
- Локальный reverse proxy с адресами по имени worktree или ветки, настраиваемым базовым доменом и плоским шаблоном hostname.
- HTTPS с предоставленными пользователем сертификатами.
- Фоновая работа после завершения CLI, состояние процессов, readiness и логи.
- Команда сборки перед запуском, проектные lifecycle hooks.
- Публикация через Cloudflare Quick Tunnel с паролем, режимы live и snapshot.
- Неинтерактивный CLI для агентов: обнаружение сервисов, предварительный план изменений, JSON-результаты и стабильные коды ошибок.
- Миграция MillDrum и проверка на втором проекте с другим набором сервисов.

После первой версии:

- GUI и полноценный TUI, поддержка Windows.
- Создание, удаление и переключение Git worktree самим runner.
- Удалённые машины, командный сервер, синхронизация между компьютерами.
- Собственный Docker orchestration, установка языков, package managers и зависимостей за пользователя.
- Зависимости между разными проектами, несколько копий одного сервиса внутри одного worktree.
- Автоматическое восстановление приложений после перезагрузки ОС.
- Встроенный универсальный watcher, автоматические циклы перезапуска после падения.
- Email-auth, постоянные публичные домены туннелей и другие tunnel providers. Собственные локальные домены входят в первую версию.

Вне ответственности утилиты: первоначальная настройка Cloudflare DNS и системного доступа к HTTPS-порту, выпуск и продление сертификатов подключаемых доменов, управление CA и trust store, API DNS-провайдеров и собственный DNS-сервер. Сертификаты и DNS пользователь готовит внешними инструментами; это не запланированные функции следующей версии.

Проект может использовать собственный watcher в команде сервиса. Для MillDrum сохранение автоматической пересборки backend входит в миграцию, но Go-специфичный watcher не становится частью универсального ядра.

## Проекты и экземпляры сервисов

Проект объединяет конфигурацию и связанные worktree одного репозитория. Имя проекта служит понятным пользователю адресом. Одинаковые имена в разных независимых checkout не приводят к молчаливому объединению. Независимый clone регистрируется отдельно. Для проекта без Git используется зарегистрированный корневой каталог.

Worktree определяется каноническим путём. Название ветки служит подписью и не является идентификатором. Два пути через symlink к одному каталогу не создают два экземпляра.

Сервис описывает команду, окружение и условия запуска. Экземпляр сервиса определяется проектом, worktree и именем сервиса. Повторный `up` того же экземпляра не создаёт второй процесс.

Любой сервис из worktree A может зависеть от сервиса из A, B или основного checkout. У каждого экземпляра собственные процесс, окружение, логи и необязательный порт. Встроенных типов backend/frontend и глобального «активного сервиса» нет. Слово «приложение» в пользовательском сценарии может означать один сервис или выбранный набор; отдельная сущность приложения в первой версии не требуется.

По умолчанию зависимости разрешаются внутри текущего worktree. Привязка к экземпляру из другого worktree задаётся явно и сохраняется в локальных настройках сервиса-потребителя. Команда изменения привязки показывает выбранный экземпляр; изменение вступает в силу при следующем запуске или явном restart потребителя. Если потребитель уже работает, CLI сообщает о необходимости restart.

Автоматический переход на другой экземпляр зависимости при ошибке запрещён. Циклические и отсутствующие зависимости обнаруживаются до запуска процессов. Выбор неоднозначного имени worktree завершается ошибкой с доступными путями.

## Конфигурация

Предлагаемый файл: `dev.toml` в корне проекта, хранится в Git. Локальные привязки worktree и runtime-состояние хранятся вне отслеживаемой конфигурации. Абсолютные пути конкретного компьютера не нужно коммитить.

Конфигурация сервиса задаёт:

- Рабочий каталог относительно корня worktree.
- Команду запуска и необязательную команду подготовки или сборки.
- Окружение и ссылки на адреса зависимостей.
- Необязательный порт, фиксированный или автоматический.
- Зависимости и readiness: HTTP, TCP либо только наличие живого процесса.
- Таймаут запуска и остановки.
- Необязательные lifecycle hooks.
- Настройки публикации, если она нужна.

Иллюстрация предлагаемой схемы, не готовая спецификация парсера:

```toml
version = 1

[project]
name = "example"

[services.api]
cwd = "."
build = "go build -o {run_dir}/api ./cmd/api"
command = "{run_dir}/api --addr 127.0.0.1:{port}"
port = "auto"
health = { http = "/health", timeout = "30s" }

[services.console]
cwd = "apps/console"
command = "pnpm dev -- --host 127.0.0.1 --port {port} --strictPort"
port = "auto"
depends_on = ["api"]
env = { VITE_API_URL = "{dependencies.api.url}" }

[services.worker]
cwd = "."
command = "./scripts/worker"
depends_on = ["api"]
env = { API_URL = "{dependencies.api.direct_url}" }

[services.console.share]
mode = "live"
auth = "password"
```

Формат команд, escaping подстановок и приоритеты окружения нужно зафиксировать в технической спецификации до реализации. Команды выполняются только при явной операции пользователя. Регистрация проекта, просмотр статуса и проверка конфигурации не запускают проектный код.

Неизвестные поля, неподдерживаемая версия схемы и некорректные ссылки дают ошибку с местом в конфигурации. Обновление файла не перезапускает работающие процессы. Статус показывает, если их конфигурация отличается от текущей.

## Запуск и остановка

`up` запускает выбранные сервисы и их зависимости в нужном порядке. Зависимый сервис стартует после readiness зависимостей. Процесс без проверки отображается как running, а не как проверенный healthy.

Обычный `up` не заменяет работающую версию. При изменённой конфигурации предлагает явный restart. Сбой сборки при restart или switch сохраняет старый процесс. Артефакты новой сборки не перезаписывают файлы работающей версии.

При частичном сбое запуска команда возвращает ошибку и перечисляет фактически запущенные сервисы. Неудачный экземпляр и его дочерние процессы очищаются. Успешно запущенные зависимости остаются доступными; состояние не выдаётся за транзакционный откат.

`down` без глобального флага относится только к текущему worktree. Он не останавливает зависимости в другом worktree. Остановка потребителя никогда автоматически не выключает его зависимости.

Если у останавливаемого сервиса есть работающие потребители вне выбранного набора, операция завершается отказом и перечисляет их. Явный `--cascade` включает потребителей в остановку. Сервисы останавливаются в обратном порядке зависимостей, публикации закрываются прежде их целей. Глобальная остановка требует явного `--all`.

Остановка завершает принадлежащее runner дерево процессов с ограниченным временем ожидания. Чужие процессы не завершаются ни по совпавшему порту, ни по устаревшему PID. После аварии CLI следующая команда сверяет registry с ОС и позволяет остановить оставшиеся процессы.

Команды управления одним экземпляром сериализуются. Конкурентные запросы не создают дубликатов; занятая операция даёт понятную ошибку для повторной попытки. Сбой одного проекта не должен запрещать чтение состояния остальных.

## Порты и адреса зависимостей

До сборки и запуска runner разрешает привязки зависимостей и составляет план адресов. Уже работающие экземпляры сохраняют свои порты. Для новых экземпляров runner выбирает порты с учётом registry всех проектов и занятости в ОС, затем фиксирует назначения под блокировкой. Фиксированный занятый порт даёт ошибку, без завершения его владельца. По возможности экземпляр сохраняет порт при restart.

После этого runner подготавливает окружение, выполняет сборку и запускает зависимости, дожидается их readiness и запускает потребителей. Адрес известен заранее, но сам по себе не означает готовность сервиса. Назначение порта в registry защищает от конкурирующих запусков runner, а не резервирует сокет ОС за произвольным приложением.

Предлагаемый контракт окружения:

```text
RDR_HOST=127.0.0.1
RDR_PORT=32101
RDR_DIRECT_URL=http://127.0.0.1:32101
RDR_URL=https://console-feature-milldrum.dev.example.com
RDR_DEP_API_HOST=127.0.0.1
RDR_DEP_API_PORT=32102
RDR_DEP_API_DIRECT_URL=http://127.0.0.1:32102
RDR_DEP_API_URL=https://api-main-milldrum.dev.example.com
```

Значения примера относятся к сервису `console` из worktree `feature`, подключённому к сервису `api` из `main`. HTTPS URL без номера порта предполагает настроенный вход на 443; при другом порте proxy номер включается в URL.

Runner передаёт только доступные значения: у процесса без порта нет `RDR_PORT`, у не-HTTP сервиса нет HTTP URL. Имена зависимостей нормализуются для переменных среды, конфликты нормализации отклоняются при проверке конфигурации. Пространство `RDR_*` зарезервировано, унаследованные значения не могут подменять вычисленные адреса.

Конфигурация отображает эти значения на интерфейс конкретного приложения: `PORT`, `HOST`, `API_URL`, `VITE_API_URL` или аргументы командной строки. Например, `env = { PORT = "{port}", API_URL = "{dependencies.api.direct_url}" }`. Runner не предполагает, что любое приложение понимает `PORT` само по себе. Вычисленные значения доступны также сборке и hooks; это необходимо для браузерного приложения, встраивающего URL API при сборке. Сборка snapshot использует адреса, пригодные для публикации, например относительный `/api`; локальный адрес зависимости не подставляется в неё автоматически.

Серверные запросы могут идти напрямую на `RDR_DEP_API_DIRECT_URL`. Код в браузере использует HTTPS URL зависимости либо относительный `/api`, направленный в выбранную зависимость. Так внутренние порты связывают процессы независимо от доменной маршрутизации.

Проверка свободного порта не гарантирует, что его не займёт другой процесс до запуска. Такой конфликт завершает текущую операцию диагностируемой ошибкой. После подготовки окружения и сборки runner не меняет порт молча; повторный запуск пересчитывает план и необходимые артефакты. Runner не объявляет сервис ready по ответу постороннего процесса. Приложения с автоматическим переходом на другой порт должны запускаться в строгом режиме.

Сервис получает адрес конкретного выбранного экземпляра каждой зависимости. После смены адреса работающие потребители помечаются как требующие restart; runner не меняет их окружение задним числом. При управляемом switch перезапускаются затронутые потребители.

По умолчанию примеры и генерируемые настройки используют loopback. Если команда приложения игнорирует переданный адрес или порт, CLI сообщает о несоответствии при проверке запуска.

## Локальные домены и HTTPS

### Адреса по имени worktree

Предлагается включить в первую версию локальный HTTP/HTTPS reverse proxy. Он даёт экземпляру постоянный адрес и направляет запросы на его текущий внутренний порт. Это развивает подход [portree](https://github.com/fairy-pitta/portree), где доступны адреса `branch-name.localhost:<port>`, HTTPS и собственные cert/key.

Основной шаблон: `{service}-{worktree}-{project}.{domain}`. Пользователь задаёт базовый домен, например `dev.example.com`, и сертификат для `*.dev.example.com`. При настроенном входе на 443 адреса выглядят так:

```text
https://console-feature-milldrum.dev.example.com
https://api-feature-milldrum.dev.example.com
https://console-main-milldrum.dev.example.com
https://api-main-milldrum.dev.example.com
```

Необязательный короткий alias, например `feature-milldrum.dev.example.com`, должен быть явно настроен, свободен и покрыт предоставленным сертификатом. Коллизия адресов даёт ошибку до изменения маршрутов, без перехвата чужого сервиса. Произвольные вложенные шаблоны не требуются для первой версии.

По умолчанию имя worktree берётся из имени его каталога; настройка позволяет использовать имя ветки либо явный alias. Имя превращается в допустимую DNS-метку. Коллизии после нормализации, длинные имена и detached HEAD обрабатываются явно: CLI предлагает задать alias. Зарегистрированный alias закрепляется за экземпляром и не меняется молча при checkout другой ветки. Смена alias выполняется явно и удаляет старый маршрут.

Полный hostname проверяется после подстановки шаблона. Маршрутизация использует registry экземпляров, а не обратный разбор имени на части. Коллизии полного имени, в том числе из-за дефисов внутри его частей, отклоняются до регистрации маршрута.

При общей зависимости потребители получают адрес одного выбранного экземпляра, например `api-main-example.dev.example.com`. Runner не создаёт фиктивный экземпляр в каждом worktree. У независимых экземпляров зависимости разные адреса.

### Proxy и работа приложений

Один фоновый proxy текущего пользователя обслуживает зарегистрированные проекты. Он запускается при `up` сервиса с включённой маршрутизацией и переживает закрытие терминала. `--no-proxy` позволяет запускать только процессы. Остановка одного worktree удаляет только его маршруты; явная остановка proxy не останавливает приложения.

В первой версии proxy слушает только loopback. HTTP- и HTTPS-порты настраиваются глобально. Основной пользовательский сценарий использует HTTPS на 443 без номера порта в URL. Пользователь заранее настраивает возможность слушать этот порт либо внешний локальный proxy, передающий запросы runner. Внешний proxy с завершением TLS должен передавать исходные Host и схему; runner доверяет таким заголовкам только от явно настроенного локального proxy. Альтернативные порты допустимы как явная настройка. Runner не запускает команды приложений от root. Если порт занят или недоступен, он сообщает ошибку и не выбирает другой порт молча.

Неизвестный Host возвращает 404, остановленный зарегистрированный сервис возвращает 503. Запрос не запускает сервис автоматически. После restart маршрут переключается на новую готовую версию; после падения proxy восстанавливает маршруты из проверенного состояния. Старый маршрут не должен вести в посторонний процесс, занявший освободившийся порт.

Локальный proxy поддерживает WebSocket, потоковые ответы и SSE. Ограничение SSE у Cloudflare Quick Tunnel не относится к локальному proxy. Проверяются HMR, редиректы, Secure cookies и передача внешней схемы и Host приложению. Входящие forwarded-заголовки нормализуются, proxy не принимает произвольную цель из запроса.

Runner предоставляет отдельные `direct_url` и `url`: прямой адрес процесса и адрес через proxy. `{dependencies.api.url}` обозначает настроенный адрес зависимости через proxy, если он включён; `.direct_url` всегда обозначает прямой адрес. Для внутренних запросов worker может использовать `.direct_url`, а браузерное приложение получает HTTPS URL или относительный `/api`. Healthchecks проверяют процесс напрямую, доступность маршрута проверяется отдельно.

Необязательный маршрут, например `/api` сервиса `console`, направляется в явно привязанную HTTP-зависимость. Это позволяет использовать один origin при общей зависимости и при независимых экземплярах. По умолчанию путь сохраняется, удаление префикса задаётся явно. Иначе проект сам настраивает CORS, allowed hosts и доверие к proxy. Runner не отключает эти проверки и не включает глобальный `allowedHosts = true`.

Разные hostname разделяют browser origins, но не гарантируют изоляцию cookies с общим атрибутом Domain. Проект должен использовать host-only cookies, если сессии worktree должны быть независимыми. Автоматическая подмена cookies и OAuth callback URL не входит в требования.

### Настраиваемый домен и сертификаты

`localhost` и его поддомены зарезервированы для loopback в [RFC 6761](https://www.rfc-editor.org/rfc/rfc6761.html#section-6.3). Совместимость проверяется с браузерами и CLI-клиентами на поддерживаемых ОС; одинаковое поведение всех системных resolver не предполагается.

Первый сценарий использует собственный домен с DNS в Cloudflare. Пользователь самостоятельно настраивает wildcard DNS для `*.dev.example.com` так, чтобы имена разрешались в loopback на его компьютере. Это локальный маршрут; Cloudflare не используется как публичный HTTP proxy для этих адресов. Runner не обращается к Cloudflare API и не требует токен DNS. Наличие сертификата не настраивает DNS. Команда диагностики отдельно проверяет разрешение имени, listener, маршрут и TLS. Собственный домен не открывает доступ из интернета, публикация остаётся отдельной операцией `share`.

HTTPS завершается на локальном proxy; приложение может продолжать слушать HTTP на loopback. Пользователь задаёт пути к готовой PEM certificate chain и private key. Поддерживаются сертификаты с точными SAN и wildcard. Runner проверяет соответствие ключа, покрытие hostname и срок действия; TLS не понижается до HTTP при ошибке. Обновлённую пару можно загрузить командой reload без остановки приложений. При ошибке reload сохраняется предыдущая конфигурация и выводится причина отказа.

Runner не выпускает и не продлевает сертификаты, не создаёт CA и не меняет trust store. Если пользователь предоставил сертификат частного CA, доверие к нему в браузере и других клиентах пользователь настраивает самостоятельно.

Wildcard в TLS покрывает ровно одну метку имени. `*.dev.example.com` подходит для `console-feature-auth-milldrum.dev.example.com`, но не для `console.feature-auth.milldrum.dev.example.com`. Для вложенного варианта нужны точные SAN или wildcard нужного уровня, например `*.feature-auth.milldrum.dev.example.com`. Источник: [RFC 9525, раздел 6.3](https://www.rfc-editor.org/rfc/rfc9525.html#section-6.3).

В первой версии используется плоский шаблон с настраиваемым базовым доменом. Пример для одного пользовательского wildcard-сертификата:

```toml
# Фрагмент локальной конфигурации, синтаксис предварительный.
[routing]
domain = "dev.example.com"
hostname = "{service}-{worktree}-{project}.{domain}"

[routing.tls]
mode = "provided"
cert_file = "/home/user/.config/rundevrun/tls/fullchain.pem"
key_file = "/home/user/.config/rundevrun/tls/privkey.pem"
```

Базовый домен можно задавать глобально и переопределять для проекта. Порты listener остаются общими; пути к ключам и машинные настройки хранятся вне Git. Несколько сертификатов выбираются по SNI. До регистрации маршрута runner проверяет, что для него есть подходящий сертификат. Ключи не передаются в окружение сервисов и не попадают в вывод диагностики.

Для публично доверенного wildcard-сертификата своего домена можно использовать внешний ACME-клиент с DNS-01. Он подтверждает контроль DNS без публичного доступа к локальному приложению. См. [Let's Encrypt DNS-01](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge). Управление DNS-токенами не входит в ответственность runner.

Первая версия поддерживает плоские адреса, proxy и загрузку готовых сертификатов. DNS настраивается вне runner. Первоначальную настройку входа на 443 пользователь выполняет самостоятельно. Runner проверяет готовые настройки и сообщает, что именно мешает локальному доступу.

## Переключение и lifecycle hooks

Switch заменяет один или несколько выбранных экземпляров сервиса версиями из явно указанных worktree и обновляет привязки их потребителей. В одной операции можно указать разные целевые worktree для разных сервисов. Выбор всей группы не подразумевает глобальное переключение проекта или всех проектов.

Для каждого сервиса задаётся соответствие исходного и целевого экземпляров. Сокращённая команда может перечислять сервисы с общими исходным и целевым worktree. Для неоднородного набора предусмотрен файл операции. Переключение всех работающих сервисов исходного worktree требует явного `--all-services`. Если целевой worktree не содержит нужного сервиса, операция отклоняется до остановки процессов.

Переключение может затронуть потребителей за пределами выбранного набора, если меняется их зависимость. План явно перечисляет такие перезапуски. Самостоятельные сервисы, не входящие в набор и не зависящие от него, продолжают работать.

Перед выполнением проверяются все соответствия, зависимости, конфигурации и доступность целей. Если целевой экземпляр уже работает, операция отклоняется; подключение к нему выполняется через `bind` и restart потребителей. Переключение допускает перерыв в работе.

Последовательность переключения набора:

1. Подготовить все новые сборки, не меняя работающие экземпляры. Ошибка подготовки сохраняет исходное окружение.
2. Закрыть затронутые публикации и остановить затронутых потребителей в обратном порядке зависимостей.
3. Для заменяемых экземпляров выполнить `before_stop`, остановку и `after_stop`. Здесь проектный hook MillDrum сохраняет офлайн-копию базы своего сервиса.
4. Выполнить `before_start`, запустить новые экземпляры в порядке зависимостей, дождаться readiness и выполнить `after_start`.
5. Обновить привязки затронутых потребителей и запустить их с новыми адресами. Потребители, сами входящие в набор замены, запускаются только в новой версии.

Каждый экземпляр останавливается и запускается не более одного раза на соответствующем этапе, даже если попадает в план по нескольким зависимостям. Адрес новой версии содержит целевой worktree; старый адрес не перенаправляется на другую версию молча. Сохранённые привязки сервисов вне набора не переопределяются значениями по умолчанию.

Операция над набором не обещает атомарность. При сбое после начала остановок выполнение зависимых шагов прекращается, CLI возвращает ненулевой код и фактические результаты по всем затронутым экземплярам: выполнено, ошибка, не выполнено. Не затронутые сбоем уже запущенные сервисы сохраняются. Агент может прочитать состояние и выполнить следующую явную операцию; молчаливого отката данных нет.

Hooks получают причину операции, идентификаторы экземпляров, старый и новый пути, доступные адреса. Они имеют таймаут и отдельные записи в логах. Прямые операции start, restart и stop используют те же hooks; hook вызывается только для реально выполняемого перехода.

Ошибка `before_stop` запрещает остановку соответствующего сервиса. Ошибка `after_stop` или `before_start` запрещает запуск его новой версии. Ошибка `after_start` отображается как ошибка операции при уже работающем процессе; его потребители ещё не запускаются. CLI показывает фактическое состояние после каждого сбоя.

Автоматического отката базы и повторного запуска старой версии после возможной миграции нет. Hook после остановки не гарантируется при SIGKILL или потере питания. Проектные hooks должны допускать повтор после прерванной операции и не вызывать рекурсивно управление тем же экземпляром. Публикации после switch не открываются автоматически.

## Состояние и логи

Общий список показывает проект, worktree, сервис, состояние, PID, прямой и именованный URL, доступность proxy, зависимости и активную публикацию. Различаются stopped, starting, running, ready, unhealthy и failed. Для ошибки доступны причина и путь к логам. Ошибка TLS или proxy показывается отдельно от состояния самого приложения.

Логи разделяются по экземплярам и запускам, доступны последние строки и follow. Сборка, hooks и приложение должны различаться в выводе. Хранение ограничено ротацией; предел фиксируется в технической спецификации. Удаление старых логов не удаляет данные приложения.

Состояние и секреты доступны только текущему пользователю ОС. Обычный статус и JSON-вывод не раскрывают окружение и пароли. Runner не обещает удалить секреты, которые само приложение напечатало в собственный лог.

Закрытие терминала или клиента GUI в будущем не останавливает сервисы. Общий системный daemon и автозапуск при входе в ОС не являются требованиями первой версии.

## Публикация сервисов

Публикация всегда запускается отдельной явной командой. Обычный `up` не делает сервис публичным. В первой версии у каждого экземпляра может быть одна активная публикация; разные экземпляры могут иметь свои туннели одновременно.

Live проксирует запущенный HTTP-сервис. Snapshot выполняет проектную сборку и отдаёт отдельную копию статических файлов, которая не меняется от последующих правок исходников. Snapshot фиксирует статические артефакты выбранного сервиса, а не состояние его зависимостей или их данных.

Для статического приложения с API в snapshot нужны явно настроенные маршруты к выбранным зависимостям, например `/api` к сервису `api`. Live использует proxy самого dev-сервера либо те же явные маршруты. Автоматической публикации всех зависимостей нет. Статические файлы и проксируемые маршруты защищены одним паролем.

Пароль генерируется при создании публикации и показывается только в ответе на эту операцию. Повторный share возвращает существующую публикацию без смены пароля; новый пароль требует явного пересоздания. Открытый пароль не хранится в registry или логах. Новый сеанс публикации не принимает cookies старого. `unshare` прекращает внешний доступ, сохраняя локальные сервисы.

Шлюз не предоставляет неявных исключений для API, OAuth или статики. Авторизация самого приложения продолжает работать за шлюзом. Нельзя переносить из MillDrum без обобщения удаление cookies, подмену Origin, CSP и встроенный login script. Поддержка cookies приложения и WebSocket проверяется отдельно; универсальная совместимость любого HMR не обещается.

Пользователь устанавливает `cloudflared` отдельно. Его отсутствие не мешает локальной разработке и даёт понятную ошибку только при публикации. Сбой туннеля не останавливает приложение.

Cloudflare Quick Tunnels предоставляют временный URL, не гарантируют доступность и не поддерживают SSE. Поэтому приложение с SSE нельзя считать полностью работающим через этот режим. Email-auth через `--allowed-mail` существует, но отложен, чтобы первая версия сохранила проверяемый парольный сценарий. Источник: [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/), проверено 13 ноября 2026.

## Предлагаемый CLI

CLI проектируется прежде всего для агента. Имена `api`, `console`, `admin` и `worker` ниже произвольны, поведение определяется конфигурацией и зависимостями.

Контракт первой версии:

- `--help` объясняет область действия, обязательные аргументы и побочные эффекты команды, приводит примеры.
- Списки проектов, worktree и сервисов возвращают стабильные идентификаторы, пригодные для следующей команды. Список сервисов включает настроенные, но ещё не запущенные сервисы.
- Экземпляр однозначно определяется проектом, worktree и именем сервиса. Путь или идентификатор worktree имеет приоритет над удобными подписями; неоднозначное имя ветки даёт ошибку с кандидатами. Ветка разрешается только в существующий checkout, runner не выполняет git checkout.
- Команды принимают один сервис или список. Для смешанного набора экземпляров из разных worktree используется структурированный файл операции; его схема входит в спецификацию CLI.
- Команды изменений поддерживают `--dry-run --json`: показывают разрешённые цели, изменения привязок, остановки, запуски и публикации, не выполняя проектные команды. При реальном запуске состояние проверяется заново; dry-run не резервирует план.
- `--json` поддерживается командами обнаружения, проверки и управления. Stdout содержит один документ результата с версией схемы, областью действия, итоговым статусом и результатом по каждому экземпляру. Прогресс и логи идут в stderr; результат не требует разбора человеческих сообщений.
- Ошибка содержит стабильный код, идентификатор экземпляра, причину и доступные следующие действия. Частичный успех имеет ненулевой exit code. Точные схемы и коды фиксируются до реализации команд.
- Команды не задают интерактивных вопросов. Неоднозначный или опасно широкий запрос отклоняется с указанием нужного явного селектора. Глобальный `down --all` нельзя спутать с `switch --all-services`, ограниченным исходным worktree.
- Повторные `up`, `down` и установка той же привязки не создают дубликатов и не перезапускают работающие экземпляры без запроса. `restart` и `switch` явно обозначают замену. После прерванного switch агент сначала читает фактическое состояние, а не рассчитывает на безопасное слепое повторение.
- По умолчанию команда ждёт завершения операции или readiness в пределах таймаута и возвращает итог. Фоновая работа самих сервисов не означает, что CLI вернул успех до их запуска.

Пример синтаксиса, который нужно закрепить в технической спецификации:

```sh
rdr register .
rdr projects --json
rdr worktrees --project example --json
rdr services --project example --worktree ./main --json
rdr config check --json

rdr up api worker --project example --worktree ./main --json
rdr up console --project example --worktree ./feature-a --json
rdr up admin --project example --worktree ./feature-b --json
rdr bind console api --project example --worktree ./feature-a --to-worktree ./main --json
rdr restart console --project example --worktree ./feature-a --json

rdr switch console --project example --worktree ./feature-a --to-worktree ./feature-b --dry-run --json
rdr switch console --project example --worktree ./feature-a --to-worktree ./feature-b --json
rdr switch api worker --project example --worktree ./main --to-worktree ./feature-c --json
rdr switch --all-services --project example --worktree ./main --to-worktree ./feature-c --json
rdr switch --file ./switch.json --json

rdr ls --json
rdr status --project example --json
rdr logs console --worktree ./feature-a --follow
rdr open console --worktree ./feature-a
rdr proxy status --json
rdr proxy reload --json
rdr proxy stop --json
rdr doctor --json

rdr share console --worktree ./feature-a --mode live --json
rdr share console --worktree ./feature-b --mode snapshot --json
rdr unshare console --worktree ./feature-a --json
rdr down console admin --worktree ./feature-a --json
rdr down
rdr down --all --json
```

Вне зарегистрированного каталога команды изменения требуют явный проект и worktree либо полные ссылки в файле операции. `ls` по умолчанию показывает все проекты. Команда без аргументов показывает краткую справку. Текстовый вывод предназначен человеку, JSON агенту.

## Миграция MillDrum

Критерий первой готовой версии: старый launcher больше не нужен для ежедневной работы с MillDrum. Проверяется функциональная замена запуска, остановки, переключения, статуса, логов, обнаружения checkout, пересборки и защищённой snapshot-публикации, а также проектных seed, backup и входа. Терминальное меню не требуется: его действия доступны через CLI. Live-публикация остаётся частью согласованного предложения первой версии.

У MillDrum остаётся тонкая обёртка `./dev`, конфигурация сервисов и проектные команды. Обёртка использует установленный runner и сообщает, если его нет.

В MillDrum остаются:

- Резервные копии SQLite и защита каталога данных от одновременного использования.
- `seed snapshot`, `seed apply` и проектная настройка окружения.
- Завершение активных агентов перед заменой backend.
- Одноразовые ссылки и коды входа, вызовы MillDrum CLI.
- Go-пересборка по изменению исходников и необходимые особенности preview.

Для параллельных backend конфигурация MillDrum задаёт разные каталоги данных. Один каталог данных нельзя открыть несколькими backend. Последовательное переключение с общей базой сохраняет текущие блокировки и резервное копирование.

Сначала новый runner проверяется в отдельном runtime-каталоге. Переход требует явной остановки старого launcher, чтобы два супервизора не управляли одними процессами. Данные приложения не переносятся и не удаляются автоматически. Старый launcher удаляется после проверки сценариев миграции.

В исходном коде на commit `1184e35` пригодны к адаптации `process.go`, `state.go`, парольный шлюз и часть `expose.go`. `session` и команды фиксированы на backend/UI/expose. `exposureHandler` содержит правила MillDrum, поэтому публикация требует отдельной проверки совместимости. Количество переносимых строк не является критерием успеха.

## Критерии приёмки

1. MillDrum и второй проект работают одновременно через один установленный бинарник без правок ядра runner под второй проект.
2. В двух worktree запущены сервисы с общей зависимостью. Остановка одного потребителя сохраняет другой и общий экземпляр зависимости.
3. В двух worktree работают независимые наборы сервисов с разными портами и данными. Остановка одного worktree не затрагивает другой.
4. Сервис подключается к зависимости из третьего worktree по явной привязке. Ошибка выбранного экземпляра не вызывает подмену другим.
5. Повторные и конкурентные `up` не создают дубликатов. Цикл зависимостей отклоняется до выполнения команд проекта.
6. Занятый порт, провал сборки, readiness timeout и ошибка hook дают ненулевой exit code, причину и точное фактическое состояние.
7. После закрытия терминала процессы работают. После прерывания CLI во время запуска их можно найти и остановить; чужой процесс с переиспользованным PID остаётся жив.
8. При switch ошибка подготовки сохраняет старые экземпляры всех выбранных сервисов. Ошибка после остановки не запускает новую версию поверх неподготовленных данных.
9. Live и snapshot доступны по паролю. Без него закрыты и статика, и API, и WebSocket. Cookies приложения работают; `unshare` прекращает доступ, локальное приложение продолжает работать.
10. Snapshot сохраняет прежние статические файлы после изменения исходников. Провал новой сборки не разрушает существующую публикацию.
11. В MillDrum проверены backup после остановки, seed, вход, завершение агентов и автоматическая пересборка. Два backend не используют одну SQLite-базу одновременно.
12. Проверки lifecycle проходят на Linux и macOS. Подключение второго проекта описано без изменения кода runner.
13. HTTP-сервисы двух worktree доступны по разным именованным URL. После смены внутреннего порта URL остаётся прежним и направляется в нужный экземпляр. Коллизия alias не перезаписывает чужой маршрут.
14. Проверены адреса вида `console-feature-milldrum.dev.example.com` с готовым wildcard-сертификатом и отдельно настроенным DNS. Неподходящий wildcard, истёкший сертификат и неверный ключ дают понятную ошибку без перехода на HTTP.
15. HTTPS работает с предоставленным сертификатом без выпуска сертификатов и изменений trust store со стороны runner. Проверены Secure cookies, WebSocket/HMR и SSE на локальном proxy; привязки соблюдаются для общих и независимых экземпляров зависимостей.
16. После остановки worktree его адрес не обслуживает другой worktree. Перезапуск proxy и reload сертификатов не останавливают приложения. Диагностика отличает ошибку DNS, занятого порта, TLS и остановленного сервиса.

17. До запуска потребителя его окружение и окружение сборки содержат назначенные адреса нужных зависимостей. Проверены общие и независимые зависимости, отображение в `PORT`/`API_URL`, конфликт порта и отсутствие молчаливого переназначения после сборки.

18. Агент обнаруживает ещё не запущенные сервисы, выбирает их по идентификаторам и управляет ими без интерактивного ввода и разбора текстовых сообщений.
19. Проверены переключение одного сервиса, выбранного набора с разными целевыми worktree и всех сервисов исходного worktree. Независимые сервисы вне плана продолжают работать. При частичном сбое JSON показывает результат каждого шага и фактическое состояние.
20. Локальные сервисы и proxy слушают только loopback. Внешний доступ появляется только после `share`. Готовые настройки домена Cloudflare используются без DNS API-токенов и автоматических изменений DNS или trust store.
21. После миграции все перечисленные ежедневные сценарии MillDrum выполняются без старого launcher. Специфика MillDrum не появляется в универсальном ядре.

## Порядок реализации

Сначала зафиксировать идентичность проекта/worktree/сервиса, привязки зависимостей и контракт конфигурации. Затем выделить управление процессами сразу для произвольного набора экземпляров, проверить общие и независимые зависимости, одиночное и пакетное переключение.

Следующий шаг добавляет локальную маршрутизацию и TLS, публикацию и hooks, после чего MillDrum переводится на новую конфигурацию. Приёмка завершается проверкой второго проекта и сбоев lifecycle на обеих ОС.

Промежуточный перенос с единственными backend/UI допустим как внутренняя заготовка, но не считается первой пользовательской версией. Оценки 5–15 инженерных дней из исходного обсуждения пока не являются обязательством: их нужно пересчитать после технического проектирования пакетного switch, snapshot, локального proxy/TLS и миграции watcher.

## Решения перед реализацией

Основные продуктовые границы определены. До реализации нужно закрепить технические контракты: схему конфигурации и файла пакетной операции, JSON-результаты, exit codes, правила hooks и точный порядок переключения графа зависимостей. Эти детали должны соответствовать описанному поведению CLI для агента.

Нужно выбрать второй реальный проект для приёмки универсальности. Это не блокирует работу над ядром. Имя бинарника `rdr` и файл `dev.toml` остаются рабочими названиями.

Первоначальную настройку Cloudflare DNS, сертификата и локального HTTPS-входа пользователь выполняет самостоятельно. Для интеграционной проверки используются подготовленные им настройки. Реализация проекта на этом этапе обсуждения ещё не начата.
